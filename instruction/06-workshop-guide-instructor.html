時間管理の最重要ポイント

止める推奨タイミングは 「テスト整備（R3）が完了した時点」または「不具合修正（R1）が完了した時点」です。詳細は §08。

01事前準備チェックリスト

前日までに

  • リポジトリを参加者ごとに用意（またはフォーク手順を用意）
  • ブランチが main-jp 相当のクリーンな状態か確認
  • ツールチェーンの確認（下記コマンド）。未導入なら導入手順を手元に
  • ポート 3000 と 8001 が空いているか確認
  • リモート環境の場合、ポート3000の受信を許可（8001は不要）
  • 成果物 HTML の閲覧手段を決めておく（§13 参照）
  • 参加者用ガイドブックを配布（講師用は配布しない）
python3 -V; uv --version; node -v; npm -v # 期待: Python 3.11+ / uv 0.4+ / Node 18+ / npm 9+ ss -ltn | grep -E ':(3000|8001)' || echo "3000 / 8001 : free"
前回はここで時間を使いました

検証環境に uv・node・npm のいずれも入っていませんでした。導入自体は sudo 不要で数分ですが、当日発覚すると流れが止まります。

導入手順は CLAUDE.md の「環境チェック」節に記載済みです。前日に一度通してください。

開始直前に

  • MCP サーバー（Playwright）の承認を済ませる。初回起動時に確認が出ます
  • 参加者に「入力を求められたら自分で打つ」ことを予告
  • 画面共有の準備。ターミナルの文字サイズを大きめに
  • ブラウザのタブを2つ用意（アプリ用・成果物用）

02進行の3原則

  1. 機能のツアーをしない。作業の流れが必要としたときに、その場で1〜2文で紹介する。冒頭で機能一覧を説明すると、以降ずっとツールの話になります
  2. 世界観を崩さない。Meridian は「クライアント」、コードは「前任ベンダーの残したもの」、作業は「案件」。「これはワークショップの課題6です」のような舞台裏の発言は避けます
  3. 参加者に決めさせる。推奨は伝えますが、順序も範囲も参加者の判断に委ねます。「R1 より先に R2 をやりたい」もそのまま通してください
前回いちばん効かなかったこと

選択肢として提示した学習項目は、ほぼ選ばれません。Plan Mode は3回提案して3回スキップ、サブエージェントも1回提示して未使用でした。

体験させたい項目は「ここでは必ずこうします」と進行上のルールにしてください。「使ってみますか？」と聞くと、作業が流れている参加者は中断を選びません。

補足資料の扱い

docs/rfp/meridian-background.md と docs/rfp/vendor-handoff.md を案内します。

  • 背景資料の価値は購買委員会3者の力学です。調達部長（予見可能性重視）、オペ担当VP（実ユーザー、前任に不満）、IT部門（テスト未整備を理由に変更を止めている）。ここに気づくと提案の質が変わります
  • 引き継ぎ資料の価値は薄さそのものです。全体55行。「既知の問題」がわずか3行。この落差が最大のリスクだと気づかせます

コードを覗きたいと言われたら

応じて構いませんが深追いさせない。「今はざっくり感触をつかむ程度にして、受注してから本格的に見ましょう」というスタンスを保ちます。ただし後述のとおり、提案書の差別化には軽い確認が非常に効きます（§05）。

確認事項のドラフト（AskUserQuestion の使いどころ）

3〜5件の質問をドラフトさせ、「もしあなたがクライアントだったらどう答えますか」という形で参加者に選ばせます。回答が提案書の前提条件になります。

前回の回答例（参考）
質問参加者の回答

成功条件

最重要 — 「必ず1箇所直す」を進行ルールにする

前回は LGTM／大丈夫です／このまま進んで が続き、修正が一度も発生しませんでした（デッキも修正0回）。作業は速く終わりましたが、このワークショップ最大の体験である「作り替えの容易さ」が未達でした。

対策として、セクション提示時に次のように言ってください。

台本例 「ここでは必ず1箇所直してもらいます。内容に不満がなくても構いません。トーン、長さ、順番、どれでもいいので1つ指定してください。直すのがどれくらい速いかを見てほしいんです。」

セクションの順序と所要目安

セクション目安この段落で見せたいこと
エグゼクティブサマリー3分要求の因果関係を整理できること（要件の羅列ではない）
技術アプローチ5分Plan Mode の提案タイミング。配点40%の本体
スケジュール3分必須を先に置き、希望項目を最後に配置する構造の意味
価格3分前提条件で範囲を守るという考え方
デッキ（HTML）6分作り替えの速さ。ここで必ず修正を1回回す
Plan Mode の入れ方（技術アプローチの前）

選択肢にせず、進行として入れます。

台本例 「次は配点40%の本体です。長くなるので、ここは Plan Mode を使います。Shift+Tab を2回押してください。押すと Claude はファイルを変更できなくなり、計画だけ出します。読んで合意してから書かせます。」

抜けるときも Shift+Tab。「入る・出る」を1往復させることが目的です。

答え — コードを軽く確認すると出てくる相違（4件）

提案段階でコードを覗くと、RFP・引き継ぎ資料の記述と実物の相違が見つかります。ここが提案書の差別化の核になるため、参加者が渋っても軽い確認は勧めてください。

資料の記述実際
「自動テストが一切整備されておらず」（RFP §2）tests/backend/ に API テストが実在（40件収集・38件パス・2件失敗）
「i18n 対応を拡張すること」（D2）locales/ と useI18n.js が実装済みで稼働中。既定ロケールは日本語
「フィルターの一部が未接続」（引き継ぎ資料）composables/useFilters.js に共通実装が存在
（記載なし）useAuth.js、server/CLAUDE.md が存在

注意：テスト件数は tests/TEST_SUMMARY.md に「55件全件パス」と書かれていますがこれは誤りです。実測は40件中38件パス。前回は Claude 自身がこの記述を検証せずに引用し、後で訂正しました。「ドキュメントを検証する」というテーマの最良の実例なので、議論で使ってください。

手順

  1. 環境チェック。CLAUDE.md の手順で4つのツールを確認。不足があればここで導入
  2. ポート確認。3000/8001 が空いているか
  3. スラッシュコマンドの説明（1〜2文）。「プロジェクトで定義できるショートカットです」
  4. 参加者に /start を入力させる。「これは私が代行するものではありません」と明示
  5. 画面を触らせる。あちこちクリックし、おかしいところを探させる
  6. Plan Mode を進行として入れる。選択肢にしない
画面を触らせるときの誘導

ヒントは探し方で出します。答えは言いません。

  • 「操作しても何も起きないものはありませんか」
  • 「他の画面と表示が違うところはありませんか」
  • 「画面Aの数字と画面Bの数字、噛み合っていますか」

開発者ツールのコンソールを開かせると発見が加速します。Reports ページを見せるのが最も効果的です（§12 参照）。

着手順の推奨

提案書の論理に沿えば R3（テスト）→ R1（修正）→ R2（新機能） です。R4（現状把握）を最初に置くとオリエンテーションを兼ねられます。ただし参加者が別の順を選んだらそのまま通してください。

R2 に入る場合の重要な進め方

R2（発注推奨）は業務ロジックを含みます。実装前に計算方法を文書化して合意するという順序を必ず踏ませてください。前回はこの順序により、仕様書に書いた判定例が実装後の実測値と完全に一致し、「合意した内容がそのまま動く」ことを数字で示せました。教育効果が非常に高い展開です。

Reports ページに集中する問題（R1 の対象）

ビュー7つのうち Reports.vue だけがすべての規約から外れています。この構造に気づけるかがポイントです。

規約他6ビューReports.vue
共通フィルターを使う準拠未使用 → 操作しても表示が変わらない
i18n を使う準拠未使用 → 画面全体が英語。通貨も USD のまま
Composition API準拠旧パターン
API クライアント経由準拠直接呼び出し
デバッグ出力を残さない全体で2箇所13箇所 → 1回の表示で約80行出力
最重要 — 原因の連鎖

API クライアントにレポート系の関数が無いため、Reports.vue は直接呼び出しをするしかなく、そこから他の逸脱が連鎖しています。

13環境トラブル対応集

症状原因と対処
シェルが突然終了する
（終了コード144）		 pkill -f vite のようにコマンド名で停止しようとすると、pkill 自身のコマンドラインに一致して実行中のシェルごと落ちます。
対処：ポート指定で止める。fuser -k 3000/tcp
前回は同じ罠を3回踏みました。CLAUDE.md に明記済みです。
lsof: command not found 環境に lsof が無い。対処：ss -ltn / fuser / netstat で代替
uv: command not found ツールチェーン未導入。対処：curl -LsSf https://astral.sh/uv/install.sh | sh → export PATH="$HOME/.local/bin:$PATH"（sudo 不要）
node: command not found 対処：nvm 経由で導入。新しいシェルでは . "$HOME/.nvm/nvm.sh" が必要
リモートから画面が開けない localhost 直書きの API 呼び出しがあると、外部 IP からは破綻します。
対処：client/vite.config.js に host: true と /api のプロキシを設定（済）。公開が必要なポートは3000のみ。8001 は不要
成果物 HTML が開けない GUI ブラウザや xdg-open が無い環境がある。
対処：client/public/ にコピーし、既存のポート3000から配信。新しいポートを開けずに済む
ブラウザ操作が失敗する Playwright のブラウザ本体が未導入。対処：ブラウザ導入ツールを実行させる（自動で対処されます）
日本語が □ になる 等幅フォントに日本語グリフが無い、または select/button が font-family を継承していない。
対処：フォールバックに和文フォントを追加、font-family: inherit を明示。実機ブラウザでは正常に見える場合があります
コミットできない Git の identity が未設定。対処：リポジトリ限定で設定（--global は使わない）
バックエンドテストが2件失敗する これは正常です。需要予測データの既存の不整合で、着手前から失敗しています。参加者に「自分が壊した」と誤解させないよう先に伝えてください
