INPUT 01

現在の在庫水準

inventory.json に発注点が定義済み。既存のバックエンドテストも「発注点以下のアイテム」を検証しています。既存の概念を土台にできます。

INPUT 02

需要予測

demand_forecasts.json と /api/demand が存在。予測をどの期間・どの粒度で推奨に反映するかを確定します。

INPUT 03

予算上限

上限内で何を優先して発注するかの基準が必要です。欠品リスクの高い品目か、金額効率か。ここが最も重要な合意事項です。

設計方針

新規ビュー Restocking.vue を Composition API で実装し、既存 composables を活用して他画面と操作感を揃えます。画面上で「なぜその品目が推奨されたか」を確認できる構成にします。

週 11 — 試用期間

実装完了と同時に納品するのではなく、Tanaka 様チームに 1 週間お使いいただき、その反応を反映する時間を計画に含めています。

D1 · D3 · D2 — フェーズ 4

D1 と D3 は、同じ課題への 2 つの側面です。

ご確認の際、D1 の基準として「倉庫フロアでの視認性を最優先に」とご回答いただきました。この一言が、2 項目の性格を決めました。

統合の判断

D1（UI モダナイズ）と D3（ダークモード）は、RFP では別項目です。しかし動機は同一です — 倉庫フロアの複数端末が低照度環境で運用されているという課題。

したがって当社は、これをひとつの設計課題として扱います。判断基準は 1 つだけ。「低照度環境で、離れた位置から、手袋を着けた状態でも確実に読めるか」

−60h / −$9,000
統合により排除した重複工数
テーマ基盤の実装を一度で済ませられるため。希望項目 2 件を実質 1 件分の工数で満たします。
  • コントラスト比を設計の起点にする。現行のスレート系デザイントークンを、低照度環境での可読性基準に照らして見直します。
  • テーマ切り替えの基盤を作る。ライト／ダークを CSS 変数として定義。基盤を作れば D3 は自動的に満たされます。
  • 情報の優先順位を見直す。「見た目を新しくする」のではなく、遠目に最初に読むべき数値が最も目立つ配置に整えます。
  • ステータス色を再検討する。低照度環境および色覚多様性への配慮から、色のみに依存しない表現（記号・形状の併用）を検討します。
  • D2 は既存基盤の適用。東京拠点 12 名の英語力にばらつきがあると伺っています。機械的な翻訳ではなく、倉庫業務で実際に使われる用語を当てます。
