00このワークショップの狙い

あなたはコンサルタントです。クライアントから提案依頼書（RFP）が届きました。まず提案書を書いて受注し、次に実際のシステムを直します。Claude Code はその相棒です。

課題やること身につくこと
課題1
前半		 RFP を読み、提案書とプレゼン資料をつくる 読解・調査・文書作成を任せる進め方。コードを書かない使い方
課題2
後半		 受注した案件として、実際のコードを直して機能を追加する 既存システムの把握、不具合の調査、テストの整備、新機能の実装
このワークショップで一番大事な考え方

Claude が出すものは「初稿」です。完成品ではありません。

あなたの仕事は、出てきたものを読んで「ここを直して」と言うことです。全部おまかせにすると、それはあなたの成果物になりません。遠慮なく差し戻してください。作り直しは数十秒で終わります。

エンジニアでない方へ

課題1はコードを一切書きません。課題2でコードが登場しますが、あなたが書く必要はありません。「何をしたいか」を日本語で伝え、出てきたものを判断する役です。技術用語が出てきたら「それは何？」と聞いてください。説明するのも相棒の仕事です。

01始める前に

あなたにしかできない操作があります

Claude が代行できない操作があります。「入力してください」と言われたら、あなた自身がキーボードを叩いてください。ここが最初のつまずきポイントです。

操作なにをするいつ使う
/ で始まるコマンドプロンプトに直接入力/start（アプリ起動）、/mcp（接続確認）など
Shift+Tab2回押すとモードが変わるPlan Mode に入るとき（後半で使います）
@ファイルを会話に引き込む資料を読ませるとき。候補が出るので選ぶだけ
!コマンドを自分で実行ログインなど自分の手で実行したいとき
覚えておくと得な感覚

「Claude にやらせること」と「自分がやること」の境目は、権限と責任が絡むかどうかでだいたい決まります。モードの切り替え、ブラウザでのログイン、コマンドの実行許可は自分側です。

環境の確認（講師の指示があれば）

後半でアプリを動かします。必要なツールが揃っているか、最初に確認します。以下は講師または Claude が案内しますので、覚える必要はありません。ただ「動かす前に前提を確認する」という順序だけ意識しておいてください。

python3 -V; uv --version; node -v; npm -v

02Session 1-1 — 状況をつかむ

SESSION 1-1課題全体紹介
5分
このセッションのゴール：自分の役割（コンサルタント）と締切を理解し、最初のファイル参照を自分の手で実行する。

あなたがやること

  1. 講師の状況説明を聞く（クライアント名・案件・締切）
  2. Claude から「一緒に読みましょう」と言われたら、自分で @ を入力して RFP を開く

入力するもの

# @ を押すとファイル候補が出ます。docs/rfp/ あたりまで打って選んでください @docs/rfp/MC-2026-0417.md を一緒に読みましょう

覚えるべきこと

  • @ でファイルを渡せる。パスを暗記する必要はなく、候補から選べます。これが今日いちばん使う操作です
  • 資料は「渡す」もの。Claude は勝手にあなたのファイルを読んでいるわけではありません。渡したものを読みます
この5分でやらないこと

Claude Code の機能一覧を覚える必要はありません。仕事の話から始めます。機能は必要になった場面で1つずつ出てきます。

03Session 1-2 — 課題文を読む

SESSION 1-2課題文の読解と Challenge / Cost の議論
10分
このセッションのゴール：RFP の要求を整理し、書かれていないこと（穴）を見つける。人手でやったらどれくらいかかるかを想像する。

あなたがやること

  1. 要約を読み、必須項目と希望項目を把握する
  2. 「この情報だけで見積もれるか？」と自問する。足りないものを探す
  3. 補足資料（クライアント背景・前任ベンダーの引き継ぎ資料）も読ませる
  4. 確認事項の質問が提示されたら、クライアント役として自分で答える

探し方 — 穴を見つけるための問い

  • 数量が書かれているか。「複数の問題」「いくつかの改善」のような曖昧な表現はないか
  • 基準が書かれているか。「モダンに」「使いやすく」は、誰が何をもって判断するのか
  • 予算が書かれているか。書かれていないなら、規模をどう決めるのか
  • 範囲の境界が書かれているか。どこまでやれば完了なのか
ここが今日の分かれ道です

RFP には意図的に曖昧な箇所があります。それを「クライアントに確認したいこと」として言語化できるかどうかが、このセッションの到達度です。

見つけた穴は、あとで質問リストになり、その回答が提案書の前提条件になります。ここで手を抜くと、後半まで影響します。

人手でやった場合を想像する

議論のために、次を頭の中で見積もってみてください。答え合わせは後半でします。

作業あなたの見積もり
RFP と補足資料3点を読んで要点を整理する_____ 時間
約9,000行のコードベースの現状を把握する_____ 日
提案書一式（5セクション）の初稿を書く_____ 日
プレゼン資料12枚をつくる_____ 日

覚えるべきこと

  • 質問を作らせることができる。「確認すべきことを整理して」と頼めば、曖昧な箇所を洗い出してくれます。レビューの相棒として使えます
  • あなたの回答が前提条件になる。質問に答えると、それが文書に反映されます。判断はあなたがするという構図を体感してください
  • 選択肢を提示させると考えやすい。「どうしますか」より「選択肢を出して」のほうが判断しやすくなります

04Session 1-3 — 提案書をつくる

SESSION 1-3Step-by-Step で RFP 解答案を作成
20分
このセッションのゴール：1セクションずつ作り、都度直すというリズムを体験する。

進む順序

  1. エグゼクティブサマリー（1ページ）
  2. 技術アプローチ（各要件への対応方針）
  3. スケジュール（フェーズ分け）
  4. 価格（前提条件つき）
  5. プレゼン資料（10〜15枚の HTML）
ここが今日いちばん重要なルールです

各セクションが出てきたら、必ず1箇所は直してください。

「これでいいです」と流すのは簡単ですが、それでは作り替えの速さという最大の体験を逃します。前回のワークショップでは修正が一度も発生せず、この学びが得られませんでした。

直すところが思いつかないときは、下の「言い方の例」を使ってください。

直すときの言い方の例

直したい方向そのまま使える言い方
トーン「もっと硬い日本語のビジネス文書にして」／「もっと率直に、断定的に」
長さ「半分の長さにして」／「この節だけ厚くして」
力点「価格より納期の確実性を前面に出して」
削除「この段落は他社批判に読まれそうなので削って」
追加「リスクと対応策の表を足して」
見た目（資料）「ダークテーマにして」／「枚数を10枚に減らして」／「順番を入れ替えて」

途中で提案されるかもしれない機能

機能誰が操作意味
Plan Modeあなた Shift+Tab ×2いきなり書き始めるのを止めて、方針だけ先に出させるモード。合意してから実装に入れます
コードを覗くClaude見積もり精度を上げるため、実物を確認します。資料の記述と実物が違うことがあります
Plan Mode は一度は入ってみてください

提案されたらスキップせず、1回は体験することをおすすめします。長い成果物や、方向を間違えると手戻りが大きい作業で効きます。前回は3回提案されて3回スキップされ、この体験が未達でした。

覚えるべきこと

  • 1セクションずつ、都度直す。まとめて全部作らせるより速く、望んだものに近づきます
  • 資料に書かれていることを鵜呑みにしない。実物を確認すると違うことがあります。「実際はどうなっているか確認して」と頼めます
  • Plan Mode は「書く前に相談する」ためのもの。入るのはあなた。Shift+Tab を2回
  • HTML の資料は作り直しが速い。色・順番・枚数の変更は数十秒です。遠慮する必要がありません

05Session 1-4 — 成果物を直す

SESSION 1-4出来上がった解答案を読んで感想を語る
10分
このセッションのゴール：生成物を自分の目で評価する。使えるか、直すべきか、足りないものは何かを判断する。

あなたがやること

  1. ブラウザで資料を開く（開き方は講師が案内します）
  2. 全ページに目を通す
  3. 少なくとも1箇所、直す指示を出す
  4. 直った結果を確認する

読むときの観点

  • これで受注できると思うか。足りないものは何か
  • 言い過ぎ・攻めすぎの箇所はないか。他社批判に読まれる表現はないか
  • 前提条件が硬すぎないか。「組みにくい相手」に見えないか
  • 自分の会社の情報が必要な箇所はどこか。そこは AI に任せられない部分です
ここで気づいてほしいこと

提案書の中でAI に埋められない項目があります。自社の実績、顧客の連絡先、社名。「どこが任せられないか」を知ることは、「何を任せられるか」を知ることと同じくらい重要です。

覚えるべきこと

  • 読んで判断するのがあなたの仕事。生成できることと、使えることは別です
  • 任せられない部分を見極める。事実・実績・連絡先など、検証できない情報は自分で埋めます
休憩（30分）

ここまでが課題1です。提案書が完成し、受注が決まったという設定で後半に入ります。後半は実際のコードに手を入れます。

休憩中にやっておくと良いこと：後半で使う画面をブラウザで開けるか確認しておくとスムーズです。

06Session 2-1 — 方向性を決める

SESSION 2-1Manual Mode で実装方向性を議論。Plan Mode も活用
10分
このセッションのゴール：いきなり書かせず、方針の合意を先に取るという進め方を体験する。

あなたがやること

  1. アプリを起動する。/start と入力（あなたが入力します）
  2. ブラウザで画面を開き、あちこちクリックしてみる。おかしいところを探す
  3. どの要件から着手するか決める（推奨は提示されますが、決めるのはあなた）
  4. Shift+Tab を2回押して Plan Mode に入る。方針だけ出させて合意する

入力するもの

# 1. アプリ起動（スラッシュコマンド） /start # 2. Plan Mode に入ってから、方針を出させる # （Shift+Tab を2回押してから入力） この要件の実装計画を立ててください

画面を触るときの観点

不具合が仕込まれています。何が仕込まれているかは書きませんが、探し方を書きます。

  • 操作しても何も起きないものはないか（ボタン、フィルター、絞り込み）
  • 表示が他の画面とちがうところはないか（言語、通貨、書式）
  • 数字が噛み合わないところはないか（画面Aの合計と画面Bの合計）
  • ブラウザの開発者ツールのコンソールにエラーが出ていないか（開き方は講師が案内します）
スラッシュコマンドとは

プロジェクトごとに定義できるショートカットです。このリポジトリには /start（サーバー起動）、/stop（停止）、/test（テスト実行）などが用意されています。Claude が代行するものではなく、あなたが入力するものです。

Plan Mode の使いどころ

Plan Mode 中は Claude はファイルを変更できません。計画だけを出します。読んで、違うと思ったら計画段階で直せます。実装が終わってから直すより圧倒的に安く済みます。

抜けるには Shift+Tab を押します。

覚えるべきこと

  • /start のようなスラッシュコマンドは自分で入力する。プロジェクトに定義されたショートカットです
  • 大きい作業の前は Plan Mode。方針を先に合意すると手戻りが減ります
  • 実装前に合意を取る価値。とくに計算ロジックや業務判断が絡むものは、先に「どう計算するか」を決めてから作らせます
  • 自分の目で画面を触る。コードを読む前に、利用者として何がおかしいかを見ておくと判断が速くなります

07Session 2-2 — 実装を観察する

SESSION 2-2Auto Mode に切り替えて自動的に進めてもらう
25分（区切りで止めます）
このセッションのゴール：連続した自動作業を観察し、どこで人が介入すべきかの感覚をつかむ。

あなたがやること

  1. Auto Mode に切り替える（講師が案内します）
  2. 手を止めて観察する。ここは見る時間です
  3. 気づいたことをメモする（下の観察シートを使ってください）
  4. おかしいと思ったら遠慮なく止めて質問する
全部終わるまで待つ必要はありません

実装をすべて終えるには時間がかかります。大きい実装が1つ終わった時点で止めて構いません。止めるタイミングは講師が判断します。観察と議論のほうが大事です。

観察シート（メモしてください）

観点気づいたこと
順番
何から手をつけたか。なぜその順か		 
調べ方
どうやって原因を特定したか		 
間違い
どこで失敗したか。どう立て直したか		 
意外だったこと
想定と違った発見		 
確認してきたこと
勝手に決めず、あなたに聞いてきたのは何か		 

観察のヒント

  • 症状から入ったか、原因から入ったか。不具合を1つずつ潰したのか、まとめて解ける根っこを探したのか
  • テストをいつ作ったか。直す前か、直した後か。それによって何が変わるか
  • 間違いをどう発見したか。自分で気づいたのか、テストが教えたのか
  • どこで手を止めて聞いてきたか。「これは私が決めるべきでない」と判断した箇所はどこか
Claude は間違えます。それを見るのも目的です

失敗は隠されません。前回は9件の間違いがありました。大事なのは「間違えたか」ではなく「どう気づいて、どう直したか」です。その仕組みを見てください。

覚えるべきこと

  • 安全網を先に作ると、その後が速い。テストを先に整えておくと、大きな書き換えも「壊していない」と確認しながら進められます
  • 症状ではなく原因の連鎖を探す。「不具合8件」が実は1つの原因だった、ということが起こります
  • 実測してから判断する。資料の記述ではなく、動かした結果・実際のデータで判断します
  • 任せる範囲に線を引く。業務判断が必要なものは実装させず、選択肢を出させて自分が決めます
  • 止めるのはあなたの判断。全部終わるまで放置しない。区切って確認するほうが安全です

08Session 2-3 — 報告書を書かせる

SESSION 2-3Project の進捗報告を書いてもらう
5分
このセッションのゴール：実装だけでなく報告の作成まで任せられることを知る。

入力するもの

ここまでの進捗報告書を書いてください（HTML で）

出てきた報告書を見る観点

  • 作業ログの羅列になっていないか。「何をしたか」だけでは報告として弱いです
  • 判断が必要な事項が整理されているか。「誰が何を決める必要があるか」が書かれているか
  • 数字に根拠があるか。実測値か、それとも推測か
  • 都合の悪いことが書かれているか。できなかったこと、間違えたことが隠されていないか
実務でいちばん効く使い方かもしれません

週次報告、月次報告、ステアリングコミッティ資料。「作業内容は分かっているが、まとめる時間がない」という場面は多いはずです。実測値にもとづく報告を数分で作れることの価値を、ここで測ってみてください。

覚えるべきこと

  • 報告書も成果物として頼める。形式（HTML / Markdown / スライド）も指定できます
  • 良い報告書には「未決事項」がある。成果の羅列より、判断待ちの整理のほうが読み手に役立ちます

09Session 2-4 — 観測を語る

SESSION 2-4観測した内容について議論する
5分
このセッションのゴール：観察したことを言葉にする。他の参加者の観察と比べる。

話す順番の目安

  1. 何を実装したか（順番も）
  2. どんな間違いをしたか
  3. 意外な発見はあったか
  4. 自分ならどこで止めたか、どこを自分でやったか
「うまくいった話」より「つまずいた話」を

成功例は資料を読めば分かります。つまずき方と立て直し方のほうが、明日からの実務に効きます。遠慮なく共有してください。

覚えるべきこと

  • 観察を言語化すると再現できる。「なんとなく速かった」ではなく「テストを先に作ったから安心して書き換えられた」と言えると、自分の仕事に移せます

10持ち帰るもの

今日の内容を、明日からの仕事に移すための対応表です。

今日やったことあなたの仕事で対応する場面
RFP の穴を洗い出し、確認事項をドラフト要件定義書・仕様書のレビュー。曖昧な記述の抽出と質問票づくり
既存コードから現状把握の資料を生成引き継いだシステムのオンボーディング。資料が無い／古い場合の初期把握
資料と実物の突き合わせ他社成果物の検収、デューデリジェンス、監査対応
テストを後付けで整備テストが無くて変更が怖いシステムへの着手
実装前に計算方法を文書化して合意業務ロジックを含む機能の設計。認識違いの事前防止
実測値にもとづく報告書の生成週次・月次報告、経営層向け資料
手順を CLAUDE.md に書き残すチームのオンボーディング資産づくり。同じ質問を二度させない
最後に考えてほしい問い

「今日の作業のうち、明日から実際に自分の仕事で試すものを1つ選んでください。」

1つで十分です。抽象的な感想より、具体的な適用先を決めたほうが定着します。

11チートシート

あなたが入力する操作

入力意味

12詰まったときは

こうなったらこうする
思った方向と違うものが出てきた途中で止めて構いません。「違います。〇〇にして」と伝えるだけ。作り直しは速いです
同じところで数回つまずいている「一歩引いて、別のやり方を提案して」と伝える。または別の要件に移って後で戻る
説明が難しくて分からない「もっと簡単な言葉で」「たとえで説明して」と頼む。分からないまま進めないでください
長すぎて読めない「3行で要点だけ」と頼む
何をすればいいか分からなくなった「いまどこまで進んで、次に何をすべきか整理して」と頼む
会話が長くなって重い/compact を入力する（あなたの操作）
アプリが起動しない講師に伝える。環境側の問題である可能性が高いです
ブラウザで画面が開けない講師に伝える。アクセス方法が環境によって違います
遠慮しないでください

「もう一度やって」「やっぱりこうして」は何度でも言えます。手戻りのコストがほぼゼロなのが、この道具のいちばんの特徴です。丁寧に頼む必要もありません。短く、率直に伝えてください。
